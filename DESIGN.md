# Why ToBeBestMe exists

ToBeBestMe is a mod that runs inside Claude Code itself, not a separate app, service, website or account. It changes Claude Code's own interface: a pane beside the chat, a line above the prompt, a tool Claude answers from, and alerts through Claude Code's own channel. There is no server, no sign-up and no API key, and everything runs on your computer. That is why it can see what no outside tool can, and why it has to be careful with it (see Trust below).

Claude Code spends three things at once, and none of them is in view while you work.

1. **Usage limits.** On a Pro or Max plan, use counts against a weekly limit, and a model can have its own. Run out and work stops mid-task until that limit resets. ToBeBestMe forecasts weekly limits; any other window Claude Code reports is listed as a limit of its own, after the weekly ones and without a forecast.
2. **Money.** With an API key, Bedrock, Vertex or team billing, every request is billed. A long chat or a looping agent can cost tens of dollars before anyone looks.
3. **Context.** Everything in the conversation is re-read on every request. As it fills up, each turn costs more, answers get worse, and auto-compaction eventually summarizes the conversation at a moment nobody chose.

And there's a fourth cost nobody counts: **keeping several projects going at once.** People run a chat per project, or per worktree, and lose track of them. Claude Code's own issue tracker has users asking for a way to see which of their parallel sessions is waiting for input ([#36885](https://github.com/anthropics/claude-code/issues/36885)), and for continuity between sessions ([#11455](https://github.com/anthropics/claude-code/issues/11455)), with community tools written just to hand work from one chat to the next. A chat that stopped to ask something hours ago is lost time, and a project picked up cold is re-explained at full price. Usage limits can run out sooner than people expect when contexts are large.

They're one problem. **Context drives the other two:** a 370k-token conversation re-sends about 370k tokens on every request, so seven requests send 2.5M input tokens. Prompt caching makes re-sent tokens a tenth of the price or less, but only while the cache stays warm, and it expires after a few minutes of inactivity.

## Who needs it

| Person | Their question |
| :- | :- |
| Subscriber in the middle of a feature | Will I hit the weekly limit before I finish? Should I switch to a cheaper model now? |
| Subscriber late in the week | I'm at 75% on Thursday. How much can I use a day? |
| API user | What did this task cost? Stop me before I spend more than $20 today. |
| Anyone in a long chat | Why does every turn cost more than it used to? What's filling my context? |
| Heavy agent user | Are helpers (subagents) burning the most expensive model on routine searches? |
| Anyone with several projects | Which project is eating my week, and is today unusual? |
| Anyone running chats in parallel | Which chat is waiting for me? Which one stopped at a limit? Where did I leave each project, and did I commit it? |
| Anyone with many skills or plugins | Why didn't my skill run? Which skills earn their place, and what is costing tokens on every request for nothing? |
| Anyone whose Claude runs workflows | What is this workflow about to do, and what might it cost? What is each agent doing right now? How do I slow it down, switch its model or stop it without losing work? What should it do differently next time? |

## What the pane answers, in this order

0. **What is waiting for me, and what is running?** Home opens on it, with any workflow running now: chats that asked you something, a permission prompt, a plan to approve, a stop at a usage limit, a pull request to review, each with its own answer buttons; then where each project got to, with loose ends such as uncommitted files.
1. **Am I OK?** One plain sentence naming whichever constraint will bind first.
2. **How long can I keep going?** About how many turns, and how much time, until each limit, budget or auto-compaction, at the recent pace.
3. **Where is it going?** Context by category, cost per turn and its trend, the model mix, helpers, tools whose output fills the context, and turns that missed the cache.
4. **What should I do?** Ranked suggestions in plain words, each with a button wherever the mod can act on it.

## The levers that actually save budget

| Lever | What it saves | How ToBeBestMe helps |
| :- | :- | :- |
| A smaller conversation (compact, or start fresh from a handoff note) | Every later turn | Shows how much each request re-sends; Compact now; Start fresh writes a note, clears, and fills an empty prompt box with a request to read the note and wait for your go-ahead; optional automatic compaction between turns. The note before a compaction is itself one more request over the conversation, so it is skipped when the chat is nearly full or has been idle |
| A cheaper model for routine work | Several times the cost per request | Automatic / Always / Off; helpers always on the cheaper model; route the main conversation too, and at a reached budget the whole chat moves. Switching model re-reads the chat once, since the cache belongs to a model, so it is done once, not turn by turn |
| Less thinking | Thinking tokens | Lower effort once context passes the warning. A change of effort also empties the cache, so the next request re-reads the chat once; it suits setting before long work |
| A warm cache | Most of the re-sent input | Cache reuse rate; flags turns that rebuilt the cache after a pause |
| Fewer always-loaded tools | Tokens on every single request | MCP tool tokens by server, with a nudge to disconnect unused ones |
| Reading through helpers | Main conversation growth | Tools ranked by how much output they added |
| Hard budgets | Runaway spend | Chat and daily budgets that warn, switch to the cheaper model, or hold new prompts |
| Skills for repeated work | Re-explaining the same thing, turn after turn | Spots prompts you repeat across projects, drafts a skill and checks it before saving, counts which skills actually run, and shows which ones cost tokens on every request without ever running |
| The right model for each stage of a workflow | About half the cost of routine stages | Ways to spend less finds checking stages (verify, recheck, walkthrough, gather) that fanned out on Opus and says what Sonnet would have cost; Run every agent on Sonnet (an answer to the go-ahead question) and Model for new agents act on a run right away |
| Workflow agents sized to the job | Setup paid per agent, and long jobs re-reading their own conversation | Finds stages of many one-item agents and agents that cost $15 or more mostly re-reading; Make it a rule… shows the line and adds it to your CLAUDE.md on Save change |
| Resuming instead of restarting | Paying again for finished agents | Resume workflow… on a stopped run; flags runs that were started over |
| A listing Claude can read | Skills that silently stop triggering | Says which skills go to Claude by name alone because the listing ran out of room, and frees it from the pane: manual-only for skills nobody runs, plugins to turn off, or more room, each shown as it is now and as it will be, and written on Save change |

## Skills that run when they should

People report skills that never trigger, or that Claude reads as documentation instead of running ([#9716](https://github.com/anthropics/claude-code/issues/9716)). Two mechanics explain much of it, both described in Claude Code's [skills documentation](https://code.claude.com/docs/en/skills). The skill listing has room for 1% of the context window; past it, the skills that don't fit go to Claude as a bare name it can't match to a request. Claude Code reports this in `/doctor` and its debug log, not in the conversation ([one user found five of 84 skills invisible](https://blakecrosley.com/blog/skills-my-agent-could-not-see)). And a description over 1,536 characters is cut. The fixes exist (`skillOverrides` to make a skill manual-only, `skillListingBudgetFraction` for more room, descriptions that say when to use them first), but the conversation doesn't show when you need them. The Skills tab does, beside the chat (`/doctor` still gives its own estimate): what Claude can see, what ran, what to fix in your own skills, and the fix for each, made in the pane.

## Running workflows with confidence

A workflow is a script Claude writes to split a big job across many agents. One run can start hundreds of agents and go for hours, and until now all a person saw was a background task, then a bill or a used-up weekly limit. The questions are the same every time: before it starts, what will it do and how big is it; while it runs, what is each agent doing and is it on track; when it isn't, how do I slow it, switch its model or stop it without losing what finished; and afterwards, what did it cost and what should change next time.

A month of heavy real-world use showed the same four leaks again and again:

- **Routine stages on the expensive model.** Verify, recheck and walkthrough stages started five or more agents each on Opus; on Sonnet the same tokens cost about half.
- **Agents that ran too long.** The costliest agents took hundreds of steps, and about half of what they cost was re-reading their own growing conversation at every step.
- **One item per agent.** Stages of hundreds of agents, where even the cheapest agent's cost was mostly loading instructions and re-reading the same files.
- **Stages waiting on one agent.** A stage waited over an hour for its slowest agent while the typical one took two minutes.

So the Workflows tab explains, shows and steers, in that order:

- **Explain by default, ask only when asked.** Every run is explained as it starts; Ask me first is a choice, since a go-ahead for every run would soon be pressed without reading. The card says what to look at: agents that would inherit an expensive chat model, a checking stage with no cheaper model named, and the likely cost from what agents cost in the person's own runs.
- **Every agent, in words.** Each agent's row says what it is doing this moment (*Editing checkout.ts*, *Run the cart tests*) and why it waits when it does (*waiting: the run is paused*).
- **Controls that never break work.** Pause, the limit on agents at once and the model all act on agents not yet started; working agents finish their step. Stop asks first and keeps what finished, and a stopped run can be resumed.
- **Savings as evidence, not promises.** Each idea says what it would have saved on the person's own runs, how it was worked out, and that two ideas on one stage overlap. Judgment stages (review, design, building, writing) keep Opus.
- **Fixed once, in the person's words.** Make it a rule… shows the rule and adds it to the person's user CLAUDE.md under its own heading when they press Save change, so every later workflow follows it.

## Less to worry about

- **One place for everything.** Home reads Claude Code's own records for every project on the computer, chats that never ran ToBeBestMe included: what waits for you, where each project got to, and the plan they share. Nothing to set up and nothing to open one by one; in the desktop app answers go straight to the chat, and the open chats join it.
- **Answer without switching.** A waiting chat's own suggested replies are buttons; each shows the message and asks before it sends. Your own words go in a field where Return sends. Outside the app, the resume command is one press away.
- **Seen from anywhere.** The line above the prompt in every chat says when another chat is waiting.
- **Everywhere by default.** One install line puts ToBeBestMe in every project and chat, in the terminal and the desktop app, so the line above the prompt is always there.
- **What you choose wins.** An automatic switch never overrides a model you picked yourself: switch with /model and the chat stays on it, even in Always mode or at a budget, and ToBeBestMe says so. When it is sending this conversation to the cheaper model, it says that too, with one press to stop. A control that quietly does nothing is worse than no control.
- **Autopilot first.** Helpers move to the cheaper model when things get tight, a handoff note is written before a compaction (told to leave secrets out, kept only if it opens with a Goal, in a folder that ignores itself in git), and Claude is told the budget once it matters. Settings opens on how much is on autopilot, as a list, so there is nothing to watch.
- **A pace, not an alarm.** For the weekly limit, a day's share that lasts until the reset, and whether today is within it.
- **The right model, suggested.** Opus for planning and review, Sonnet for code, the cheaper model for reading; one press switches this chat when the limits call for it.
- **Told once, not nagged.** A notification goes out once per computer, whichever chat notices first. There are at most four in ten minutes, and a sound never holds up the pane. Claude Code's own notifications are unreliable outside three terminals, so ToBeBestMe also uses the Notification Center, a sound and, if you like, your phone.
- **Alerts say who, never the command.** A chat that starts waiting on you alerts once for that wait, by default, with who is waiting and what kind of wait; never the command or the file. A notification about another waiting chat carries its title and a short excerpt, so SECURITY.md says where those words go and warns that a public phone topic can be read. The next useful prompt shows only as the box's dim suggestion, and Claude can read where things stand from a read-only status tool that loads only when Claude looks for it. Its overview gives counts; titles and short excerpts come from its waiting topic as quoted data, and Claude Code asks first unless you have allowed the tool.
- **The week, to keep.** Usage can draw the week as one report card to save and share; it is one row of buttons (Save, Copy, Show preview) until its picture is asked for, project names can be hidden first, what it says wraps at any width so no figure in it is cut short, and nothing is uploaded.
- **The phone gets a short lobby**, not the pane: what waits, the limit that binds first, what runs.
- **A button does its job where you pressed it.** A fix, a setting or a rule is worked out in the background and shown in the pane as it is now and as it will be, then written on Save; it never goes through the conversation or the prompt box. Only buttons that hand Claude a job (start a workflow, resume one, a long run, try a skill) go to the conversation, because that is where Claude works and where you read its plan.
- **The right tool, suggested.** When a request looks like a job for a workflow, it says so once and offers a shape with a model per stage. The request goes into the prompt box for you to read first.
- **Long runs planned up front.** The /long-run playbook breaks big work into checked stages on the right models and stops cleanly before a limit, so a run doesn't die mid-task. It asks the status tool at each checkpoint (finding it with ToolSearch if it is not loaded). A /long-run skill file saved earlier keeps its old text until you press Save again.

## Making it easy to understand

- **Lead with the answer.** The headline says the most pressing thing in a sentence, with its one best action as a button; the detail sits one tab away.
- **Show pace, not only fullness.** Each thing that can run out has a runway: the fill is what is used, and a strand under it is how much of the window has passed, so being ahead of the clock is a length you can see. When the pace runs a limit out early, the run-out shows as a stop and a dry line to the reset: it changes shape as well as color, so it never rests on color alone. It is square-ended and horizontal on purpose: concentric rings hide how far the window has gone. Press a runway's name to open that runway's tab. Usage draws the same runway; its chart of the window so far is under Show details.
- **Count the benefit.** Every suggestion that can be counted says what it saves ("each later turn re-reads about 470k fewer tokens"), and **Wins** says what ToBeBestMe has already saved.
- **Forecast rather than alarm.** Usage limits are judged by their window's own average pace, which counts nights and breaks, and drawn as a forecast: use so far, the projected line, and where it would run out.
- **Early has to mean early.** A limit that runs out minutes before it resets anyway is not an alarm; one that runs out a day early is. The headline goes to whichever bites first among the ones that matter.
- **Explain on hover.** Rows, tiles and charts say more when you point at them, in a card drawn over what is above, so nothing moves under the pointer. The charts' own tooltips fade and rise in over 150 ms, and appear at once with reduced motion set. **Show details** puts every card's words in place for keyboards, screen readers and touch.
- **One primary action per view.** On desktop the tab bar is a segmented control (the open tab filled, the others quiet text), so the one white button is always the thing to do next. Every other choice in the pane (On and Off, a preset, the view of a list) is the same segmented control in the same track, so a choice looks alike wherever it is made; the terminal, with no fill, checks the one in force instead. Buttons say what they do: "Review workflow", "Refresh runs", "Copy run ID".
- **Every width.** Tables drop the columns that don't fit a narrow pane, and charts draw at the pane's width so their labels stay at 11px. Every box may shrink below its longest line, so a long chat title or branch name truncates instead of pushing the next column off the pane. The e2e suite checks every view at 375, 768, 1280 and 1920 pixels, with long titles and branch names in the data, and its renderer sizes boxes as the app does rather than letting them all shrink.
- **Controls beside the figures.** Budgets and how costs show are set on Usage, the check before a workflow on Workflows, MCP servers and memory from This session; Settings holds the rest, the cheaper model and the usage alert included. Each control has one home: anywhere else it would be useful, a line says where it stands and a link goes to it (Usage says how the cheaper model and the alert are set beside the limits they stretch, Settings links to Usage and Workflows for what is set there), and a suggestion whose button already exists on the tab links to it, so no control is drawn twice.
- **The one filled button answers the headline.** On This session it is the fix for what the headline says: a fresh start when the context window is what runs out first, the cheaper model for helpers when a limit does, Go to the chat to answer when a workflow waits for its go-ahead (which is then the headline). With nothing wrong there is no filled button, and no "all good" is said over a problem the headline names.
- **A heading for each section, and nothing else.** A section is a heading above a faint gray group, with no icon tiles. The line that explains a section shows under Show details, so the page stays quiet; a line that carries a fact (how old a reading is) stays.
- **Color names a thing, or says it is in trouble.** Each limit keeps one vivid color wherever it is drawn: the weekly limit blue, a model's own weekly limit a lighter blue, context cyan, budgets cornflower. Each project gets a color of its own (the six most used, from a hash of the project so it stays put), worn in the week's bars, the projects list, the busiest project and Pick up. A model family keeps one color everywhere it is drawn (Opus blue, Sonnet purple, Fable indigo, Haiku cyan). No identity color is red, amber or green, or close to one: those three mean status alone, and the identity palettes (projects, context categories, model families, limits) are blues, purples and cyan, each a mid tone that reads on a dark pane and a white one, so a legend dot is the color of its bar. Amber means past your alert or running out early and red means nearly out; either one takes over a limit's own color, so the color that says trouble is the same everywhere. Green means all is well. Charts carry the system's light-theme variants of the vivid colors, and the neutrals read on both, so a drawing stays legible whichever way the appearance is reported.
- **Show the real thing.** The welcome tour embeds the live line above the prompt and the person's own limit, so what they learn to read is what they will see tomorrow, not an illustration. It waits while anything needs an answer, and a person can leave it at any step.
- **The week on a calendar.** The tightest limit is drawn large, with the days of its window under it, "Now" over the playhead and the run-out and reset in words over their posts. Under the runway, each day's work is a bar in that day's column, stacked by project in each project's color, so the week's fill and the work that made it sit on one calendar; a day says what it held on hover, and today's name is bold. The other limits sit under it as runways of their own, so every limit is in the hero and nowhere else on Home. It is the same runway as everywhere else, made big enough to read at a glance; labels are dropped, never overlapped, when the pane is narrow.
- **Show where you are heading, not only where you are.** A runway's fill is the past; a faint ghost ahead of it is where the window's own pace lands by the reset, and the hero says the same in a sentence. A saving suggestion shows its effect on that forecast before it is pressed, so a choice is made with its consequence in view. The hero reads like a summary should: the big figure, one sentence, the chart.
- **Things respond, and live things move.** The calendar is a control as well as a picture: a day or a project pressed is picked out where it is drawn (the rest step back rather than disappear), a line says what it held, and the list beside it follows; one press brings each back. Motion means "working now" and nothing else: a soft pulse on a running workflow or chat, switched off with reduced motion set. The pane redraws once a minute, so Now and every "ago" keep time; the forecast drawings are redrawn at the quarter hour, and a drawing whose data has not changed is never reloaded.
- **Every tab opens on its one answer.** Home's hero set the pattern, and each other tab has its own: a headline with its glyph, a line of facts, one big figure at the far end when one number answers the headline, and under them the drawing that shows it. **This session** answers whether it will make it: the cost, and the context window drawn as a runway with a post where Claude Code compacts, a ghost for the next turns at the recent pace, and a bar per turn climbing towards a dashed line. **Usage** answers where the limit is heading (its forecast with the readings taken, its own reading as the figure, in its status color, and the past 7 days' work said under it) and where the week went (each day stacked by project, then projects and models as split bars); the weekly report card is one row of buttons below them, its picture a press away. **Workflows** answers what is running and what it has cost (each run a runway: cost against its limit or expectation, the work done as the strand, a stop where the cost would pass the limit first), or what the month cost and how much of it could have been saved; its figure is what the month cost. **Skills** answers whether Claude can see them: the listing as a runway against its room. **Settings** answers how much is on autopilot, and whether what it reads could be read: a source that was read and found nothing is said so, and one that could not be read says what to do next, never what the system answered. It has no figure, since its headline says the count. A tab has one of these and no tile strip above it.
- **Light and dark are both tested.** Drawings carry light-theme variants of their vivid colors, and of their words (the white of "Now", the gray of labels, amber and red text); words drawn as text that cannot follow the appearance use a color that reads on both (`midHex`). The e2e suite draws the real states on a light pane and holds text to 4.5:1 and colored marks to 3:1.
- **The window's first day is the window's.** The records keep each transcript's use by hour as well as by day, so the first bar of the week's calendar counts only what came after the window opened, not that morning.
- **One count for what waits.** Chats stopped for an answer, pull requests to look at and a workflow asking for its go-ahead are counted once (`waitingCount`), and Home, its Needs you card, the line above the prompt and the phone say it in the same words: one chat, one pull request or one go-ahead is said as itself, a mix is "9 things are waiting for you" with what it is made of under it, and the list says "Showing 4 of 8" beside its "Show 4 more". Nothing says "nothing is waiting" unless the records were read: with them unreadable Home says "Can’t tell what’s waiting" (amber, with the error and its one action first), and with reading every project off it says it is only about this chat. The go-ahead, being the one thing that blocks work, comes first on Home with the view's one primary button, which hands the keys back to the chat's own question, and the tour waits behind it.
- **Lists show their first and fold the rest.** Needs you draws its most pressing chat whole and the others a line each; Pick up does the same with its latest project, and Skill ideas shows three.
- **The line above the prompt is a glance.** Each figure takes an equal share of the row, its runway long enough to show pace, its percentage in its status color; the headline's line carries the chat's and the day's figures.
- **Say each thing once.** Home has no strip of figures and no plan card: today's figures are in the headline's line, the week's total beside Projects, the limits in the hero. The left column is what to do (Needs you, Running now, Pick up, what stands out, habits); the right is where things are (Projects, Open chats). With nothing for the right, the left takes the width.
- **Habits, not tips.** Home suggests up to three things at a time under Worth doing next (with how many of the things worth setting up are done), each one press away and each derived from the person's own settings and records: what the records show costing them first (MCP servers re-sent with every request, skills that never run), then habits they don't have yet (notifications, a skill for a repeated prompt, a memory file, a first workflow, a spending guard). Not now puts one off for a month. The card goes away when there is nothing left to suggest.
- **One name, one format, one number.** A model is written as `modelName` writes it ("Opus 5.5"; a family on its own, "Opus"), never as its id. A forecast span in a headline or an alert is rounded the way `roughSpan` rounds it ("about 33 hours"); only an exact span (a row, a duration) is written as `fmtSpan` writes it ("32 h 38 min"). A cost past the whole weekly limit is said in weeks ("1.5 weeks’ worth"), not "150%", and a share comes before its dollars. Today, everywhere it is shown, is never less than this session. A history line (the activity list) says it is as it was at the time.
- **Narrow is designed.** Below about 60 columns a value stacks under its label in words instead of ending in an ellipsis; a table gives up its bars before its numbers; the line above the prompt keeps its headline and button on a phone and drops the rest. A waiting chat's label sits on its own line, and its words start at what is asked.
- **Guidance is body size.** Text a person acts on (what to do, why) is body size in a quiet color; the small footnote size is for captions and labels. Secondary buttons (copy a command, set aside, copy an id) are quiet text, so the decision buttons are the only ones with a fill, and a card with the same action several times gives it fill once.
- **Failures look like failures.** A record that can't be read is drawn with a status color and glyph and says what to try next. A source that found nothing gets a neutral dot, not a check.
- **Hide what's empty.** A section with nothing to show stays out of the way instead of drawing an empty box.
- **Settings as presets.** Preset choices with Other… for an exact value; the essentials first, Advanced on request.
- **Plain words.** Usage limits, Weekly limit, Spending rate, Helpers (subagents), Reused from cache. Each term Claude Code uses (context, compact, handoff note) gets a one-line explanation where it first appears.
- **Every number has words beside it.** "$0.25 last turn", "resets Sun 9:00 PM", "about 18 turns (1 h 40 min)".
- **Color carries meaning, never decoration:** status (warning, error), identity (each runway, each model) or a saving, always with words beside it that say the same thing.
- **Suggestions come with a button** wherever the mod can act; otherwise they say exactly what to do.
- **Sensible defaults.** Everything works untouched, and every setting carries one line saying what it does.
- **Empty states teach.** "Shows after a few turns", not a blank space.
- **Nothing destructive without asking.** Compact and Start fresh confirm first; resetting numbers confirms; a reply Claude suggested shows the whole message before it goes to another chat.

## Trust

ToBeBestMe reads everything Claude Code records, so it has to earn that trust:
- It says what it reads, writes, runs and sends, row by row (Settings › What ToBeBestMe reads, and SECURITY.md).
- It treats text from other chats as data: cleaned, never run, and framed as quoted data wherever it goes into a prompt or a tool answer.
- It keeps what it needs in one JSON file of its own in your Claude Code configuration folder (at most 4 MiB), including short excerpts of prompts, recaps and questions from your other projects, the list of running chats as `claude agents --json` last returned it, and the prompts you repeat across projects that skill ideas are made from; turning off Read every project deletes those and the pull requests it read, and Forget stored data on the Settings tab forgets everything, spending ledgers included, so a daily budget then counts again from this chat.
- The status tool allows itself without a prompt only for figures, counts and the name of the busiest project. Its waiting topic names your other chats, so Claude Code still asks, unless you have an allow rule or bypass mode, which is your own consent.
- It never opens `.env` or key files, and takes two skill settings from Claude Code's settings files for its checks. A fix to a setting reads the whole settings file and holds its text in memory only until you press Save change or Cancel.
- It ships checksums and signed build provenance with each release, and checks its own files against its manifest daily. That check shows damage and changes after install; the release's checksums and provenance are what prove a download.

It stays open source under MIT, because a tool that reads your transcripts should be one you can read.

## Settings

Every setting is a `userConfig` field, so it appears in Claude Code's own `/config` menu and in the pane's Settings tab, or beside what it governs (budgets and how costs show on Usage, the check before a workflow on Workflows), with one source of truth. Changing it in either place saves it to Claude Code's settings and reloads the mod.

| Group | Settings |
| :- | :- |
| Budgets | Chat budget, Daily budget, When a budget is reached (warn / cheaper model / hold prompts), Cost alert every |
| Usage limits | Alert at, Warn when a limit will run out early, Show costs as (Automatic / Share of limit / Dollars) |
| Cheaper model | Use the cheaper model (Automatic / Always / Off), Cheaper model, Helpers always use it, Main chat too, Think less past the warning, Effort to use |
| Context | Warn at, Cheaper model at, Compact automatically at, Handoff note before compacting, Keep the plan through compaction |
| While you work | Check each workflow before it runs, Suggest workflows, Run budget, Line under each answer, Line above the prompt, Open the dashboard in every chat, Status line, Read every project, Notifications, Notify through, Alert when this chat waits for you, Suggest the next prompt, Pull requests and CI in Needs you, Play a sound, Say alerts aloud, Tell Claude where the budget stands |

A web address for your phone is set in the Notifications card. It is marked sensitive, because each notification's words go there.

## Honest limits

- **Cost** is what Claude Code's own ledger reports (`/cost`). On a subscription it's the API-price equivalent rather than a bill, but it's still a good measure of how heavy the work is.
- **Usage-limit percentages** come from the API's responses. The pace is the window's own average (use so far over the time the window has run), so it shows from the first reading; readings ToBeBestMe takes add the recent pace and the forecast line.
- **Tool output sizes** are estimated as characters ÷ 4.
- **Cache expiry** is inferred from large cache writes after a pause; it isn't read directly.
- **Today** is every project's records on this computer, never below this chat's own share, and it reads the same on every tab. The daily budget is enforced on the per-chat ledger of the chats that run ToBeBestMe, from Claude Code's exact costs, and wherever it is shown it says it is what counts toward the daily budget.
- **Every project's figures** are list-price estimates from the token counts in Claude Code's transcripts, read on this computer only.
- **Replies, archiving and the plan card** use the Claude desktop app's own session tools (`SendMessage`, `send_message`, `archive_session`, `get_usage`). They are not part of the documented mod interface, may change without notice and are not supported by Anthropic; the pane says so when one fails, and a terminal gets the resume command instead.
- **A paused workflow's hold** is a short `sleep` that Claude Code does not meter: an agent that has not started waits in it until the run is resumed or its limit raised.
- **What waits for you** is read from where each transcript stopped. A permission prompt leaves no trace there, so it shows only for chats running now (`claude agents --json`).

## The desktop pane's visual language

The pane in the desktop app is deliberately bold, and it is the only surface that is; the terminal does not change at all. Everything below is drawn only where `k.hasSvg` is true, as SVG with CSS inside it.

- **Hero figures.** The tightest limit's percentage on Home and each tab's lead figure are drawn big, in a gradient whose two colors are its status's: amber for a warning (a limit past its alert or running out early), red for what is nearly out or used up, green when all is well, and the neutral accent blue for a figure that is information and no status (what a month of workflows cost, a chat's cost with no budget set). The figure is bold and it says something: a gradient is never a tab's color chosen for the look of it, so a blue figure never sits over an amber headline. Each figure answers its tab's headline (Usage's is the limit the headline is about). The gradient's ends are pulled until the digits hold 4.5:1 on a dark and on a light pane. The terminal draws the same figure as plain text.
- **The glow is for what is live.** A hero figure always has its status-colored gradient. The soft bloom under the digits is drawn only while something is working (a running workflow, a chat mid-turn) or a limit is at its critical level. It sits inside the figure's own drawing, so it is always under the words and fades out before the drawing's edge (fainter on a light pane).
- **Live states.** Only the dot on a chat waiting on you or a running workflow loops. The run-out marker pulses three times when its tab opens and then stays still; nothing else moves once a tab has settled.
- **Runways that move.** The fill sweeps in from the left when its tab opens and a band of light crosses it once; the projected ghost carries a slow sheen that plays twice; the run-out marker pulses three times; and the stretch of the window after the run-out is hatched, so "out" is a texture as well as a color.
- **Week bars.** Each bar springs up from its baseline a beat after the one before it, and then stays still: nothing falls into it, because motion means something is working now.
- **Entrances play once.** The app draws the pane afresh on every redraw, and every turn redraws it, so an entrance tied to the drawing would replay each time a figure moved. Instead `settleMotion` runs each entrance from when its tab was opened: a redraw part-way through carries it on, and one after that draws the finished state, whose markup stops changing, so the app keeps the image it has. The pulse, halo, sheen and live ring are started a tab-age into their cycle (a negative animation-delay, in tenths of a second), so a drawing whose figures change carries them on, and a loop that has run its course is drawn finished. One limit is known: a drawing left unchanged keeps its entrance styling, so an app-side remount (as opposed to a change of tab) would replay it.
- **How a drawing is kept safe to draw** (the `Svg` contract in the mod types, which `e2e/lib/render.mjs` follows where the types state a rule and otherwise approximates). Every drawing carries a non-blank description for a reader who cannot see it, and its markup stays within the 131,072 characters the types allow. A still drawing is an image and an interactive one a script-less sandboxed frame, so the kit's `Svg` gives every drawing an explicit size (a drawing with none takes only the markup's own), and one stretched to its slot (`preserveAspectRatio="none"`) gets a width wider than any pane. The mod also relies on no stacking order between boxes: an absolutely placed box can paint over the boxes around it, so nothing decorative is ever placed behind words that way. The e2e checks hold every drawing to these rules, and each interactive one to a conservative rule of the mod's own (no script, foreignObject, image, link, on* attribute or vector-effect).
- **Rules that still hold.** Words are 4.5:1 or better in dark and light and never under 11px; amber and red mean status; every animation is switched off under `prefers-reduced-motion: reduce`, and the decorative marks (the sheen and the halo) are then not drawn at all; the still drawing is always the finished one.
